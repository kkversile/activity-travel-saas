# Codex Task: Implement Multi-Outlet Vendor Management in VOYA (End to End)

You are working inside `voya-vendor-platform`, containing:
- `activity-saas-backend`: NestJS 11, Prisma 6, PostgreSQL, Jest
- `activity-saas-frontend`: React 19, TypeScript, Vite, Vitest

## Goal and fixed business rules
One legally registered vendor business operates multiple outlets. Example: ABC Adventures owns outlets A, B, C and D. An individual outlet employee must have a separate login and see/manage only their authorized outlet(s). The master vendor OWNER logs in once, sees a consolidated dashboard, and can switch among all four outlets. Each outlet may use a distinct verified bank account or share the same existing verified bank account. Products, availability, bookings, fulfilment, earnings and reports must be outlet-scoped. Existing single-outlet vendors and all current bookings/financial records must continue to work.

Assume one legal entity/PAN/GST per master vendor (`Tenant`). Do NOT merge genuinely separate legal entities under one legal onboarding/KYC. Document this business assumption in the implementation and make expansion possible without implementing legal-entity grouping now.

## Implementation rules
1. Keep ONE existing VENDOR `Tenant` as the master business, with vendor-wide onboarding/KYC/legal identity. Do NOT create four Vendor `Tenant` records or separate applications.
2. Add `VendorOutlet` with UUID, tenantId, outletCode (unique within tenant), name, optional location/contact, ACTIVE/INACTIVE status, default flag if useful, timestamps and audit. Add indexes and tenant-constrained references.
3. Add `UserOutletAccess` with userId, outletId, active and unique `(userId, outletId)`. Preserve `User.organizationRole` for functional permissions; this new model controls which outlets the user may access. One user may be granted several outlets. An OWNER of that vendor has access to all its outlets (no need to materialize N memberships); other vendor roles only their assignments. Never allow a non-owner access to all outlets by omission or client-supplied identifiers. Super-admin impersonation remains read-only.
4. Add `VendorBankAccount` owned by Tenant with encrypted account number, masked number, bank name, IFSC, holder, account type, bank proof/verification status, optional currency, active flag, timestamps; allow an outlet to reference the same bank-account row as another outlet. Reuse `secret-crypto` encryption and mask utilities; never persist plaintext account numbers, expose ciphertext, or return full details in list APIs. Validate selected bank account belongs to the vendor and is verified before any new release. Bank verification must follow a real existing/admin verification flow; do not falsely mark newly entered accounts verified. Keep existing onboarding/profile semantics, reconcile legacy bank data carefully, and do not silently treat a masked-only profile as having a usable full account number.
5. Add an outlet relationship to `Product` (one primary owning outlet in v1; do not silently clone products). At agent booking creation derive `Booking.outletId` on the server from its selected Product and persist it immutably. Maintain consistency in booking failover/reallocation and prohibit unintended outlet reassignment after there are bookings/ledger entries. Include outlet in snapshots where appropriate; preserve historical attribution even if product moves.
6. For derived inventory/sessions/resources/rate plans/media/revisions/promotions/mappings/manifest/vouchers/fulfilment, enforce outlet via owning product/booking. Avoid redundant outlet columns where a reliable parent relationship suffices. Audit direct-ID read/write endpoints, bulk actions, imports, CSV/XLSX/PDF exports, scheduled reports and asynchronous workers, not just list pages.
7. Implement a centralized backend `VendorOutletAccessService` (plus helpers/guards as useful): require tenant; determine allowed outlets; for OWNER allow `ALL` only on approved aggregate read endpoints; non-OWNER with one assigned outlet can default to it; with multiple assigned outlets require explicit valid selection; for mutations always resolve exactly one outlet. Validate every object belongs to the selected outlet AND tenant, including nested foreign keys, before update/delete/confirm. Return a non-leaking 403/404 as appropriate. Reject cross-vendor assignment at DB/service boundaries. Do not trust client `outletId`, JWT-only stale roles or frontend hiding.
8. Extend existing team invitations so owner can invite a user to one or more outlet(s). Invitation preview and acceptance must preserve/commit outlet assignments atomically in the existing registration transaction. Existing vendor invitations and owners must still work. Ensure invitee cannot self-upgrade role/outlet grants. Add owner-only endpoints to change memberships and disable/remove access, including stale access revocation. Audit bank/team changes.
9. Add owner-only outlet creation/edit/activate/deactivate UI and endpoints, assign bank, manage authorized users. Define safe behavior when deactivating an outlet that has future bookings, inventory or unsettled payments: block new listings/sales but retain readable records and complete valid existing obligations; never hard-delete historical data.
10. Update vendor dashboard, products, bookings, availability, fulfilment, performance, payouts, promotions, team/reports and downloadable files. In `VendorShell` add outlet selector: OWNER = `All Outlets` + each outlet, assigned employees = only allowed outlets (hide selector if one). Place current scope clearly in the shell. The selection must drive API filtering, refetch/caches and browser navigation; reset when switching accounts/logout and avoid showing stale data from previous outlet. Prefer explicit query/DTO parameters with strict server validation; if adding a common request header, limit it to authenticated vendor requests and validate server-side. Aggregate only for OWNER.
11. Finance must use immutable event attribution: add `outletId` to FinancialEvent where needed (booking-linked events inherit booking outlet; manual vendor adjustments MUST explicitly indicate outlet or be clearly modeled as vendor-wide), and add outlet-aware settlement/batch/payout scopes. Decide and document rules for vendor-wide adjustments/holds and preserve finance correctness. Keep one settlement/payout PER OUTLET for a period even if two outlets share bank account, with beneficiary snapshot at payout creation/release. Redesign `assertNoWeeklyVendorPayout` as an outlet-aware invariant with correct concurrency locking/uniqueness; avoid payout code collisions (current public code is vendor/week-level). Update previews, fingerprints, adjustments, event allocation, maker-checker approvals, holds, release, reconciliation, CSVs, commission invoices and refund paths. Do not break tenant-wide legal tax obligations/invoicing: maintain legal identity at Tenant level. Historical payouts must remain immutable; bank changes must not rewrite previously issued/released payouts. An unavailable/unverified beneficiary must place payout on hold rather than be silently released.
12. New registration creates a default outlet as part of vendor provisioning (or an idempotent equivalent). Add additive expand/backfill/contract migrations for existing vendors: create one default outlet for each vendor tenant; attach existing products, bookings and unambiguously linked financial rows; inspect orphan/inconsistent rows and report them, do not guess. Preserve legacy payout/invoice IDs and immutable economics snapshots. Idempotent migration scripts, counts, rollback plan and verification queries. Do NOT reset or push the database schema or mutate production data. Do NOT require all columns NOT NULL before backfill. All schema changes through committed Prisma migrations.
13. Preserve current API compatibility where possible. Existing single-outlet users should continue with no new selection friction. Admin/agent/public routes must continue to function; only restrict a vendor's data based on that vendor's outlet memberships, without hiding legitimate products from authorized agent marketplace discovery.
