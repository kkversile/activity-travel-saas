# Voya Phase 9.2 — Final Finance Operations Closure

## Scope

Phase 9.2 freezes Settlement after closing Finance operations, audit boundaries, optimistic concurrency, evidence capture, currency-safe presentation, and reproducible verification. No new settlement formula or supplier-quality scope was added.

## Transactional integrity

Vendor adjustments and settlement-hold creation/release run in serializable transactions. The authoritative vendor, booking, or financial event is revalidated inside the transaction. The financial fact/hold and its AuditLog write use the same transaction client; an AuditLog failure therefore rolls back the mutation. Hold release locks the row, transitions ACTIVE to RELEASED once, and returns an already released row without another audit entry.

FinanceConfiguration updates lock the singleton and require the current `expectedVersion`. Existing VendorSettlementPolicy updates lock the policy and require `expectedVersion`; first creation is the only versionless path. Weekly-day, active/review, cycle, trigger, and delay validation occurs before the write. Stale writes return stable conflict codes.

## Outbox policy

Audit is mandatory for Finance mutations. Outbox is emitted in the same transaction for meaningful settlement and payout workflow transitions: batch creation/readiness, payout release, release failure, retry readiness, reconciliation, and reconciliation-required outcomes. Hold create/release and configuration/policy updates are intentionally Audit-only because no downstream notification consumer currently exists. Documentation does not claim that every Finance mutation emits Outbox.

## Admin evidence workflow

The Settlement Control Tower uses only supported policy values: Manual, Daily, Weekly, and Post service (`MANUAL`, `DAILY`, `WEEKLY`, `POST_SERVICE`). It represents every collection mode: `UNCONFIGURED`, `VOYA_COLLECTS`, `AGENT_COLLECTS`, `VENDOR_COLLECTS`, and `EXTERNAL`, with copy that describes evidence/state behavior rather than payment execution.

Release, failure, and reconciliation require an operator dialog. Release requires a real external payment/reference ID; failure requires the actual reason and supports an optional reference/note; reconciliation requires an explicit amount and reference. No `DEMO-*` or `RECON-*` evidence is generated by the production UI. Unresolved cancellation liabilities are presented in Reconciliation with Booking, original/final Vendor payable, and server-computed signed adjustment resolution.

Reconciliation displays human-readable blocked-reason copy and allows complete eligible settlement lines to be selected or omitted while retaining the authoritative preview fingerprint.

## Currency safety

Vendor Earnings groups KPI amounts by currency and formats each batch, payout, and legacy payout with its own currency. Admin aggregate amount KPIs are grouped by currency; counts may remain global. Unlike currencies are never summed into one amount.
